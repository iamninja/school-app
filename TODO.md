  New "Business" tab (`components/teacher-business-settings.tsx`, self-contained like `TeacherQuizBuilder`) over two new tables, split by sensitivity. `public.business_profile` (singleton row, no `teacher_id`, `is_teacher()` RLS) holds business name/ΑΦΜ/ΔΟΥ/ΚΑΔ/address — all non-secret, since it's printed on every receipt. `public.integration_settings` holds per-provider `active_environment`/`enabled`.
  Credentials were the one genuinely hard call, so it went to an **Opus design consult and then a full Opus security audit** (matching the earlier "Opus audit" passes on this list). Verdict adopted: keep secrets out of `public` entirely, because this project issues `authenticated` JWTs to students and parents — a credentials table in `public` would have only an RLS policy standing between a parent's session and the tax-authority keys, forever, across every future migration. `private.integration_credentials` lives in a schema outside PostgREST's exposed list, which turned out to be even stronger than planned: PostgREST returns `PGRST106` for it regardless of grants or policies, *including for `service_role`*. That forced a mid-implementation design change — the app now reaches the table exclusively through four `SECURITY DEFINER` functions in `public` whose `EXECUTE` is granted solely to `service_role` (verified directly: `proacl` shows only `postgres` and `service_role`; anon/authenticated can neither reach the table nor call the functions).
  Values are AES-256-GCM encrypted in app code (`lib/secrets.ts`) with `BUSINESS_SECRETS_KEY` held in Vercel env — a *different trust domain* than the ciphertext, so a Supabase-only compromise (leaked backup, PITR restore, `db dump`, an accidental future grant) yields nothing usable. Deliberately not Supabase Vault: Vault still requires `service_role` to decrypt, so it improves backup-safety but not access control, and keeps the key in the same place as the data. Audit-driven hardening beyond the obvious: ciphertext is AAD-bound to `(provider, credential_key, environment)` so a sandbox blob can't be promoted into the production row and still decrypt; decryption **fails closed** on an unrecognised version prefix rather than the tempting "assume legacy plaintext and return it", which would silently turn the column into a passthrough and skip tag verification entirely; one row per environment, so rotating production never destroys the sandbox credentials.
  `getDecryptedCredential` deliberately lives in a `server-only` module and **not** in the `"use server"` actions file — every exported async function there is a callable HTTP endpoint whether or not a client imports it, so putting it there would have shipped a public, unauthenticated plaintext-credential oracle. `tests/business-settings-actions.test.ts` asserts the actions module's exact export list so that stays enforced rather than remembered. The active environment is resolved internally from `integration_settings` rather than accepted as a parameter — two sources of truth is how you end up filing real tax documents from a test path, or filing nothing when you thought you had.
  Tests: crypto round-trip/fresh-IV/tampering/fail-closed/both AAD-promotion cases; server-action authorization guards (a non-teacher must be rejected *before* the credential store is touched, since the service-role client bypasses RLS and the app gate is the only boundary on that path); and `tests/rls/business-settings.test.ts` against real Postgres, asserting the *error* rather than an empty result set — with no grants PostgREST returns permission-denied, so `expect(data).toHaveLength(0)` would have passed on a typo'd table name or a missing fixture, i.e. for entirely the wrong reason.
